# 07 数据库设计与迁移规范

> 文档状态：Active
> 适用版本：v1.6。历史结论和旧路径仅作回溯，当前实现以本分支代码、配置和实时验证为准。
> 权威边界：migration 是物理结构权威；本文是数据库设计与演进唯一规范；生成的数据字典和 ER 图是只读派生产物。

## 角色入口

主负责人：数据库与迁移负责人。补充阅读：[09 测试规范](09-测试规范.md)。任何数据库结构变化必须新增版本化 migration，不修改已应用脚本。

## 环境与基线

| 配置 | 数据库 | 当前迁移入口 |
| --- | --- | --- |
| `dev` / `prod` profile | MySQL 8.0 | `backend/src/main/resources/db/migration/` |
| `local` / `test` profile | H2 MySQL 模式 | `backend/src/main/resources/db/migration-h2/` |
| 既有库历史兼容 | MySQL / H2 | 对应 `*-legacy/` 与既有 Java migration |

当前最终基线为 B215。新环境从 B215 启动；既有库继续扫描 legacy 并通过 validation。详细边界见 [数据库最终基线 B215](../database/database-baseline-v215.md)。

## Flyway 规则

1. MySQL 与 H2 的版本号、业务语义和关键约束必须对称；差异较大时分别维护，并由迁移行为测试证明语义一致。
2. 已执行的 `V*.sql` 永不修改；结构或数据修复只能追加 `V{next}__description.sql`，迁移前执行只读 preflight。
3. 文件使用 UTF-8；所有 profile 保持 `validate-on-migrate=true`。
4. 使用 `scripts/check-flyway-immutability.sh` 或 `.bat` 检查已提交 migration 不可变性。
5. 不以恢复旧脚本、关闭 validation、修改 checksum、`repair` 或手工改表代替新增迁移。

## 标准字段词典

| 语义 | 标准定义 | 约束与例外 |
| --- | --- | --- |
| 主键 `id` | `BIGINT` | 应用分布式 ID；禁止自增与业务编码混用 |
| 租户 `tenant_id` | `BIGINT NOT NULL` | 租户业务表必备；核心 FK 优先使用 `(tenant_id,id)` 组合关系 |
| 业务状态 `status` | `VARCHAR(32) NOT NULL` | 必须有 CHECK、注册表或代码契约；审批状态统一为 `approval_status` |
| 业务编码 | `VARCHAR(64)` | 租户内唯一；允许删除后重建时使用活动唯一键 |
| 金额 | `DECIMAL(18,2)` | 人民币元；禁止 `FLOAT/DOUBLE`；入账时按业务规则统一舍入 |
| 数量 | `DECIMAL(18,4)` | 库存、计量数量；单位成本可使用 `DECIMAL(18,6)` |
| 比例/税率 | `DECIMAL(8,4)` 或明确更高精度 | 必须说明百分数或小数口径，不得混用 |
| 业务日期 | `DATE` | 只表达自然日，不以零点时间替代 |
| 时间点 | `DATETIME` | 应用和数据库统一 Asia/Shanghai 业务口径；跨系统接口显式记录时区 |
| 审计时间 | `created_at/updated_at DATETIME` | 禁止同一模型再引入 `create_time/update_time` |
| 审计用户 | `created_by/updated_by BIGINT` | 系统任务使用约定系统用户，不使用无语义的 `0` |
| 软删除 | `deleted_flag TINYINT NOT NULL DEFAULT 0` | 仅 0/1；可复用业务键配活动唯一键 |
| 备注 `remark` | `VARCHAR(500)` | 不承载状态、关联键、审批配置或结构化明细 |
| 多态类型 | `business_type/source_type VARCHAR(64)` | 必须登记到 `sys_type_registry`；核心链仍需显式 FK |
| JSON 文档 | `LONGTEXT` + `JSON_VALID` + 1 MiB 上限 | 必须有 schema/version；敏感字段禁止进入通用 JSON |

## 唯一性与逻辑删除

主键统一为 `id BIGINT NOT NULL PRIMARY KEY`。

新增唯一约束前必须归入以下且仅以下一类：

1. **可复用业务编码**：采用生成列 `active_unique_token`；活动行固定为 `0`，删除行使用自身 `id`，允许删除后重建。
2. **永久幂等事实**：外部事件号、来源明细生成的会计或成本事实永久唯一；纠错使用冲销事实，不删除原事实。
3. **关系边**：唯一键包含租户和两端 ID，并以 tenant-aware FK 防止跨租户关系。
4. **历史快照**：使用版本号或生效区间，确保同一时点只有一个有效版本，不用当前态唯一键覆盖历史。

活动唯一键示例：

```sql
active_unique_token BIGINT GENERATED ALWAYS AS
  (CASE WHEN deleted_flag = 0 THEN 0 ELSE id END) STORED,
UNIQUE KEY uk_tenant_code (tenant_id, code, active_unique_token)
```

禁止把 `deleted_flag` 直接放入可复用编码唯一键，也禁止 nullable token 作为活动行唯一性依据。`deleted_token` 属于已退役 legacy 兼容方案，不得恢复；历史 migration 只供回溯，不修改原文件迎合当前规范。B215 MySQL/H2 基线、V210 legacy 退役迁移及 `MigrationSoftDeleteBehaviorTest`、`MigrationIntegrityTest` 是当前验证入口。

## 状态、枚举与多态键

- 审批生命周期只使用 `approval_status`；领域状态只在存在独立状态机时保留。
- Java 常量、工作流注册表、`sys_type_registry` 和 migration seed 必须通过契约测试保持一致。
- 新状态值必须同步更新 CHECK/注册表、代码枚举、接口文档和状态迁移测试。
- 不允许通过备注、JSON、CSS 类名或前端字典值暗示后端业务状态。

## JSON 使用边界

- JSON 只用于外部原文、可演进配置或低频审计快照；影响金额、权限、状态或关系的字段必须拆成类型化列或子表。
- 每个 JSON 对象顶层必须包含 `schemaVersion`；升级须向后兼容或提供显式转换器。
- 单字段上限 1 MiB；更大文件进入对象存储，数据库只保存摘要、哈希、对象键和处理状态。
- 数据库执行合法性和大小 CHECK；应用执行业务 schema 校验，任一层失败都拒绝写入。

## FK、索引与查询投影

- 核心资金、权限、库存、合同和项目关系使用 `(tenant_id, foreign_id)` 指向父表 `(tenant_id,id)`，数据库层拒绝跨租户关联。
- 外键列必须有满足左前缀的索引；高频列表索引按“租户、过滤状态、业务时间、主键”设计。
- Repository/Mapper 禁止新增裸 `SELECT *`；跨租户绕过拦截器的 SQL 必须显式列投影并显式包含租户条件。
- 面向 API 的原始 `Map<String,Object>` 只用于兼容边界；核心事实使用 Entity、DTO 或 RowMapper。现有裸 `SELECT *` 基线只能下降。
- 不盲目增加单列索引；高频查询必须用执行计划或等价证据证明索引匹配。

| 场景 | 建议索引 |
| --- | --- |
| 租户查询 | `(tenant_id)` 或组合业务键 |
| 项目列表 | `(tenant_id, project_id)` |
| 合同业务 | `(tenant_id, contract_id)` |
| 审批任务 | `(tenant_id, approver_id, task_status)` |
| 来源幂等 | `(tenant_id, source_type, source_id)` |

## 注释与可维护性

- 新表必须有中文表注释；新字段说明业务语义、单位、枚举、是否快照及是否可变。
- 既有缺失注释可由生成数据字典补足检索性，并在模型发生业务变更时以新 migration 补齐物理 COMMENT。
- “需要确认”的推断不得写成数据库 COMMENT，必须先由领域负责人确认。

## 容量、归档与分区触发线

默认不提前分区。满足任一条件时提交容量评审：

- 单表超过 1,000 万行或每月增长超过 100 万行；
- 热数据超过 365 天且 90% 查询只访问最近 90 天；
- 关键查询在合理索引下 P95 超过 500 ms，或同比增长超过 2 倍；
- 单表超过 50 GiB，备份恢复时间无法满足既定 RTO；
- 审计、导入或 OCR 原文超过 1 MiB，显著推高数据库压力。

评审顺序：修正查询和索引 → 冷热归档 → 按业务时间分区。当前只有本地环境；缺少非本地容量证据不得成为当前实施阻塞，也不得伪造环境结论。

## 结构变更验收

1. 旧库整改任务在授权范围内执行 `scripts/database/database-remediation-preflight-v194.sql`。
2. 从空库分别执行 MySQL/H2 全量 migration。
3. 在本地 dev/test/demo 升级副本执行 `scripts/database/database-remediation-postflight.sql`；所有 `BLOCK` 项为 0，`REVIEW` 项取得业务或数据负责人确认。
4. 执行迁移、契约、并发、权限、金额守恒和相关运行态验证。
5. 使用 `scripts/database/generate-schema-docs.ps1` 重新生成数据字典和 ER 关系，并审查差异。

## 禁止事项

1. 手工改表后不补 migration。
2. 修改已执行 migration、绕过 validation 或伪造 Flyway 记录。
3. 使用浮点数存金额。
4. 无 WHERE 条件批量 `UPDATE` / `DELETE`。
5. 绕过租户或项目范围全表查询。
6. 以生成文档、历史计划或旧环境结果替代当前 schema 与验证证据。
