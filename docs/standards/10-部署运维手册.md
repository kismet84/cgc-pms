### Compose 本地配置预检（PowerShell）

从仓库根目录显式传入本地环境文件和 Compose 文件，禁止依赖当前 shell 恰好已有同名变量：

```powershell
if (-not (Test-Path -LiteralPath 'deploy/.env')) {
    throw '缺少 deploy/.env，请从 deploy/.env.example 初始化本地专用配置'
}

docker compose --env-file deploy/.env -f deploy/docker-compose.dev.yml config --quiet
if ($LASTEXITCODE -ne 0) {
    throw "Compose 配置预检失败，exit=$LASTEXITCODE"
}
```

`deploy/.env` 必须包含非空 `MINIO_ACCESS_KEY` 与 `MINIO_SECRET_KEY`，且不得与 `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` 复用。服务账号及最小权限策略按 [11 安全规范](11-安全规范.md) 创建，真实值只写入被 Git 忽略的本地文件或受控 Secret，不得写入命令、日志、报告或聊天。

常规后端刷新使用 `python scripts/rebuild.py backend`；该脚本的本地兼容回退不能替代上述配置预检。若验收目标是 Compose 配置本身，现有容器健康或 `docker inspect` 只能作为运行态证据，不能替代 `config --quiet` 成功。

## 非本地部署参考（FROZEN_REFERENCE）

### 文件生命周期迁移预检（V277+）

现有数据库启动新后端前，先以只读账号执行：

```bash
mysql --batch --raw < scripts/preflight-file-lifecycle-migrations.sql
```

结果必须为零行。任一返回行表示V277活动文件名或V278/V279前64位唯一键会碰撞：停止Flyway和应用启动，导出对应`tenant_id/business_type/business_id`全部文件元数据及对象哈希，由业务所有者逐项确认保留、逻辑删除或迁移方案后另行实施；禁止自动改名、覆盖对象、伪造扫描状态或猜测去重。处置后重跑预检，仍非零不得继续。V280只修正规范小写SHA识别的MySQL大小写语义，不替代此前迁移预检。

```bash
cd deploy
cp .env.example .env
# 编辑 .env：修改密码、JWT secret、CORS 域名、MinIO 密钥
# 生产机补充：chmod 600 .env && chown root:root .env
mkdir -p ssl
docker compose -f docker-compose.prod.yml up -d
```

生产 `.env` 必须修改：数据库密码、Redis 密码、MinIO 密钥、JWT secret、CORS 域名、HTTPS 证书路径。

### 新环境数据库与首个管理员

新建环境由 Flyway B215 直接创建最终 schema 和系统白名单，默认没有用户、项目、材料、库存或业务单据。首次管理员初始化必须使用 `deploy/config/bootstrap.example.yml` 与外部 Secret：

1. 核对目标为新建 dev/test/demo 或经独立批准的新生产环境；本流程不授权重建既有生产库。
2. 注入 `CGCPMS_BOOTSTRAP_ADMIN_PASSWORD` 等变量并临时设置 `CGCPMS_BOOTSTRAP_ENABLED=true`。
3. 启动后确认 `PLATFORM_ADMIN=COMPLETED`、仅一个管理员和一条 `SUPER_ADMIN` 关系。
4. 首次登录立即改密，删除/轮换 Secret，恢复 `CGCPMS_BOOTSTRAP_ENABLED=false` 后重启。

冲突或缺密钥时禁止使用 Flyway `repair`、手工提权或把密码写进 YAML/镜像。完整步骤见[数据库最终基线 B215](../database/database-baseline-v215.md)。

### 生产密钥文件约束

1. `deploy/.env` 是**本地/目标主机专用文件**，只能从 `deploy/.env.example` 初始化，禁止从聊天记录、仓库快照、压缩包或旧主机直接复制历史密钥。
2. `deploy/.env`、`deploy/ssl/server.key` 当前已被 `.gitignore` 命中，但这只能防止**再次提交**，不能替代密钥轮换。
3. 如任一密钥曾离开目标主机或被误传到制品、工单、CI 日志、聊天工具，必须按“已泄露”处理并轮换：`JWT_SECRET`、`JASYPT_ENCRYPTOR_PASSWORD`、`MYSQL_ROOT_PASSWORD`、`MYSQL_PASSWORD`、`REDIS_PASSWORD`、`MINIO_ROOT_PASSWORD`、TLS 证书/私钥。
4. 建议把真实生产密钥放在主机级 secret 管理（systemd `EnvironmentFile`、CI/CD secret、Vault/KMS），仓库中仅保留 `deploy/.env.example` 模板。

### 生产凭据轮换与外部验收清单

若未来启用非本地部署且重新授权，生产凭据不得放入仓库级 GitHub Secrets。真实值只允许由目标主机 secret 管理、Vault/KMS 或等价受控设施注入；仓库、聊天、工单和验收报告只记录版本、指纹摘要后 6 位、时间、责任人和结论。

外部运维执行时按以下顺序操作，任一步失败即停止并保留旧版本，不得先销毁回滚凭据：

1. 双人确认目标环境、变更窗口、影响服务、回滚负责人和最近可用恢复点；禁止连接或重置生产数据库来代替凭据轮换。
2. 在受控设施中分别生成 `JWT_SECRET`、`JASYPT_ENCRYPTOR_PASSWORD`、`MYSQL_ROOT_PASSWORD`、`MYSQL_PASSWORD`、`REDIS_PASSWORD`、`MINIO_ROOT_PASSWORD` 与 TLS 新版本；不同系统不得复用同一值。
3. 先更新依赖端与消费端的受控配置，再滚动重启对应服务；数据库、Redis、MinIO 凭据必须保证服务端账号与应用消费端在同一窗口切换。
4. 验证健康检查、登录签发与鉴权、数据库读写、Redis、MinIO 上传下载和 HTTPS 证书链；只保留脱敏结果，不保存请求头、Token、连接串或密钥原文。
5. 验证通过后失效旧版本；失败时恢复旧版本并回滚服务，不得在状态不明时同时删除新旧版本。
6. 由执行人与复核人共同填写下表。缺少轮换时间、版本标识、双人复核或旧版本失效证据时，生产轮换不得判定完成。

| 对象 | 新版本/指纹后 6 位 | 保管位置 | 验证结论 | 旧版本状态 | 执行人/复核人 | 时间 |
| --- | --- | --- | --- | --- | --- | --- |
| JWT/Jasypt | `<redacted>` | `<vault-or-host-secret>` | 待填写 | 待填写 | 待填写 | 待填写 |
| MySQL | `<redacted>` | `<vault-or-host-secret>` | 待填写 | 待填写 | 待填写 | 待填写 |
| Redis | `<redacted>` | `<vault-or-host-secret>` | 待填写 | 待填写 | 待填写 | 待填写 |
| MinIO | `<redacted>` | `<vault-or-host-secret>` | 待填写 | 待填写 | 待填写 | 待填写 |
| TLS | `<redacted>` | `<certificate-store>` | 待填写 | 待填写 | 待填写 | 待填写 |

GitHub Actions 仅允许保存测试或部署编排实际消费的 Secret。当前 CI 的 `CI_TEST_JWT_SECRET`、`CI_MYSQL_PASSWORD`、`CI_MYSQL_ROOT_PASSWORD` 属于非生产测试契约；若未来增加生产自动部署，必须先创建受保护的 `production` Environment，配置审批人和允许分支，再使用 Environment Secrets，禁止退化为仓库级生产 Secret。

Windows PowerShell 执行 MySQL/Docker 轮换时，原生命令可能把正常 warning 或 Compose 进度写到 stderr；不得仅凭 stderr 判失败，应同时检查 `$LASTEXITCODE` 和目标状态。执行前必须验证旧凭据、health gate 和本机绑定，执行后必须验证新凭据、容器实际注入、旧 JWT 失效、新登录和数据表数量；中途失配时先恢复账号与运行态，再继续轮换。

### Git 历史泄露应急核查

当前仓库只读核查建议至少执行一次：

```bash
git log --all -- deploy/.env deploy/ssl/server.key deploy/ssl/server.crt
git rev-list --all --objects | grep -E "deploy/\\.env$|deploy/ssl/server\\.(key|crt)$"
git check-ignore -v deploy/.env deploy/ssl/server.key deploy/ssl/server.crt
```

处理口径：

1. 当前可达历史**查不到**敏感文件，不等于所有分叉仓库、旧 clone、CI artifact、制品缓存都安全。
2. 当前可达历史**查得到**敏感文件时，本仓库内禁止直接重写历史；应先完成密钥轮换，再由代码托管平台管理员处理缓存、fork、release artifact、镜像层与备份清理。
3. 无论历史核查结果如何，只要旧审计或事件记录表明存在泄露嫌疑，都要保留轮换记录和平台侧处置记录。

### 备份调度（systemd timer）

`scripts/backup-scheduler.sh` 统一调度 MySQL + MinIO 每日备份，可通过 systemd timer 或 cron 定时执行。

**systemd timer 配置**（推荐）：

创建 `/etc/systemd/system/cgc-pms-backup.service`：

```ini
[Unit]
Description=CGC-PMS Daily Backup
Requires=docker.service
After=docker.service

[Service]
Type=oneshot
User=root
EnvironmentFile=/opt/cgc-pms/deploy/.env
ExecStart=/opt/cgc-pms/scripts/backup-scheduler.sh all
StandardOutput=append:/var/log/cgc-pms-backup.log
StandardError=append:/var/log/cgc-pms-backup.log
```

创建 `/etc/systemd/system/cgc-pms-backup.timer`：

```ini
[Unit]
Description=CGC-PMS Daily Backup Timer
Requires=cgc-pms-backup.service

[Timer]
OnCalendar=daily
Persistent=true
RandomizedDelaySec=300

[Install]
WantedBy=timers.target
```

启用并启动：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now cgc-pms-backup.timer

# 查看状态
sudo systemctl status cgc-pms-backup.timer
sudo systemctl list-timers --all | grep cgc-pms

# 手动触发一次
sudo systemctl start cgc-pms-backup.service
```

**cron 替代方案**（不推荐，但可用于简单环境）：

```bash
# crontab -e
0 2 * * * /opt/cgc-pms/scripts/backup-scheduler.sh all >> /var/log/cgc-pms-backup.log 2>&1
```

### MySQL binlog 与 PITR（Point-In-Time Recovery）

启用 MySQL binlog 可以在全量备份基础上实现任意时间点恢复。

**推荐配置**：

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| `log-bin` | `mysql-bin` | binlog 文件名前缀 |
| `binlog-format` | `ROW` | 行级复制格式，最安全 |
| `expire_logs_days` | `7` | binlog 保留 7 天 |
| `binlog-row-image` | `FULL` | 记录完整行数据（含前后镜像） |
| `sync-binlog` | `1` | 每次事务刷盘（生产必须） |

**Docker Compose 启用方式**（`deploy/docker-compose.prod.yml` 或 `deploy/docker-compose.dev.yml`）：

```yaml
services:
  mysql:
    image: mysql:8.0
    command: >
      --log-bin=mysql-bin
      --binlog-format=ROW
      --expire-logs-days=7
      --binlog-row-image=FULL
      --sync-binlog=1
```

**PITR 恢复流程**：

```bash
# 1. 停止应用
docker stop cgc-pms-backend-dev

# 2. 恢复全量备份
./scripts/restore-mysql.sh /opt/cgc-pms/backups/mysql/cgc_pms_full_20260620_020000.sql.gz

# 3. 应用 binlog 到指定时间点
docker exec -i cgc-pms-mysql mysqlbinlog \
  --start-datetime="2026-06-20 02:00:00" \
  --stop-datetime="2026-06-20 14:30:00" \
  /var/lib/mysql/mysql-bin.* \
  | docker exec -i cgc-pms-mysql mysql -u root -p"${MYSQL_PASSWORD}" cgc_pms

# 4. 启动应用
docker start cgc-pms-backend-dev
```

### MySQL 恢复

使用 `scripts/restore-mysql.sh` 从 mysqldump 备份恢复数据库：

```bash
# 查看用法
./scripts/restore-mysql.sh

# 恢复压缩备份
export MYSQL_PASSWORD="$(grep MYSQL_ROOT_PASSWORD deploy/.env | cut -d= -f2)"
./scripts/restore-mysql.sh /opt/cgc-pms/backups/mysql/cgc_pms_full_20260620_020000.sql.gz

# 恢复明文 SQL 备份
./scripts/restore-mysql.sh /opt/cgc-pms/backups/mysql/cgc_pms_full_20260620_020000.sql
```

恢复后 Flyway 会在下次后端启动时自动执行迁移，无需手动干预。重启后端并验证健康检查：

```bash
docker restart cgc-pms-backend-dev
curl http://localhost:8080/api/actuator/health
```

### MinIO 备份注意事项

`mc mirror` 备份 MinIO 时，**必须使用 `--overwrite` 而不是 `--remove`**：

| 参数 | 行为 | 风险 |
|------|------|------|
| `--overwrite` | 覆盖目标中已存在的同名文件 | ✅ 安全 — 不会删除额外文件 |
| `--remove` | 删除目标中存在但源中不存在的文件 | ❌ 危险 — 如果源端误删或配置错误，目标文件会被永久删除 |

`scripts/backup-minio-mirror.sh` 已采用 `--overwrite`（不含 `--remove`）。如需清理目标端过期文件，使用 MinIO bucket 生命周期策略（`mc ilm`）或独立的过期清理脚本。

## MinIO 健康检查

后端提供了 Actuator HealthIndicator 用于 MinIO 连通性监控。

健康检查端点：`GET /api/actuator/health`

MinIO 组件响应示例：

```json
{
  "status": "UP",
  "components": {
    "minio": {
      "status": "UP",
      "details": {
        "endpoint": "reachable"
      }
    }
  }
}
```

故障时：
```json
{
  "status": "DOWN",
  "components": {
    "minio": {
      "status": "DOWN",
      "details": {
        "error": "IOException: Connection refused"
      }
    }
  }
}
```

**注意**：当 `minio.enabled=false` 时，`MinioHealthIndicator` Bean 不会被创建（`@ConditionalOnBean(MinioClient.class)`），`/actuator/health` 中不包含 `minio` 组件。

## 监控

至少监控：
- 后端健康检查端点和 error 日志
- 后端访问日志中的 `HTTP_ACCESS` 记录，至少采集 `traceId`、`requestId`、`method`、`path`、`status`、`durationMs`、`clientIp`
- MySQL 连接数、慢查询、磁盘
- Redis 可用性（尤其关注 `BLACKLIST_UNAVAILABLE` 日志 — 见下方 TokenBlacklistService）
- Nginx 4xx/5xx
- 审批待办积压

### 访问日志上下文

后端每个 HTTP 请求都会由 `TraceIdFilter` 输出一条 `HTTP_ACCESS` 日志，并在响应头返回：

| 字段 | 来源 | 用途 |
|------|------|------|
| `traceId` / `X-Trace-Id` | 请求头传入或后端生成 | 串联接口响应、异常日志与一次请求链路 |
| `requestId` / `X-Request-Id` | 请求头传入或后端生成 | 对接网关、Nginx 或客户端请求编号 |
| `method`、`path`、`status` | Servlet 请求/响应 | 定位接口、状态码和异常比例 |
| `durationMs` | 服务端过滤器计时 | 识别慢接口 |
| `clientIp` | `X-Real-IP`、`X-Forwarded-For` 或远端地址 | 排查来源 IP |

采集系统可按 `HTTP_ACCESS` 关键字过滤访问日志；本轮不接入外部监控平台。

### Prometheus 指标导出

后端已接入 Micrometer Prometheus，指标暴露在 `/api/actuator/prometheus`。该端点只接受独立 `MONITORING` 机器账号的 HTTP Basic 认证；业务 JWT、管理员会话、空口令和错误口令均不得抓取指标。

**Prometheus 抓取配置**（`deploy/monitoring/prometheus.yml`）：

```yaml
scrape_configs:
  - job_name: 'cgc-pms-backend'
    metrics_path: '/api/actuator/prometheus'
    basic_auth:
      username: 'cgcpms-monitor'
      password_file: '/run/secrets/monitoring_scrape_password'
    static_configs:
      - targets: ['backend:8080']
```

本地监控启动步骤：

1. 编辑 `deploy/.env`，加入宿主机密钥文件路径；密钥文件本身不得提交 Git：

```dotenv
MONITORING_SCRAPE_PASSWORD_FILE=./secrets/monitoring-scrape-password
```

2. 独立执行以下命令，叠加 dev 与 monitoring Compose，确保 backend 和 Prometheus 挂载同一只读密钥：

```powershell
Set-Location deploy
docker compose --env-file .env -f docker-compose.dev.yml -f docker-compose.monitoring.yml up -d backend prometheus
```

生产 Compose 同样只读取 `MONITORING_SCRAPE_PASSWORD_FILE` 指向的只读文件，不接受 Compose 或 `.env` 中的明文抓取密码。轮换时先原子替换密钥文件，再重建 `backend` 与 `prometheus` 服务；用旧口令返回 `401`、新口令可抓取才算完成。Prometheus UI 仅绑定宿主机回环地址 `127.0.0.1:9090`。

**最小指标清单**：

| 指标类别 | 指标示例 | 说明 |
|---------|---------|------|
| JVM | `jvm_memory_used_bytes`, `jvm_gc_pause_seconds` | JVM 内存与 GC |
| HTTP | `http_server_requests_seconds_count` | 请求量和耗时 |
| 连接池 | `hikaricp_connections_active` | 数据库连接池 |
| CPU | `process_cpu_usage` | 进程 CPU 使用率 |
| 审计持久化 | `operation_audit_persistence_total{result="failure"}` | 通用操作审计写入失败计数；大于 0 触发告警 |

### MySQL 备份与恢复

#### 全量备份

使用 `scripts/mysql-backup.ps1` 执行 MySQL 全量备份（通过 Docker `mysqldump`，无需本地安装 MySQL 客户端）：

```powershell
# 设置环境变量
$env:MYSQL_ROOT_PASSWORD = "your-root-password"

# 执行备份
powershell -ExecutionPolicy Bypass -File scripts\mysql-backup.ps1 -BackupDir "D:\backups\cgc-pms\mysql"

# 指定备份目录
powershell -ExecutionPolicy Bypass -File scripts\mysql-backup.ps1 -BackupDir "D:\backups\cgc-pms\mysql"

# 自定义保留份数（默认保留最近 7 份）
# -RetentionDays 是兼容参数名，参数值实际表示最近 N 份，不表示天数
powershell -ExecutionPolicy Bypass -File scripts\mysql-backup.ps1 -BackupDir "D:\backups\cgc-pms\mysql" -RetentionDays 30
```

备份命名规则：`{database}_full_{yyyyMMdd_HHmmss}.sql.gz`

保留策略按备份生成时间排序，仅保留最近 N 份；当前兼容参数名仍为 `-RetentionDays`，不要按自然日解释或配置。

Windows 脚本必须保持 SQL 字节流原样：`mysqldump` 输出直接重定向到临时文件后以二进制流压缩，恢复时以二进制流解压并导入。禁止先捕获为 PowerShell 字符串再重编码，否则中文等非 ASCII 数据可能损坏并在恢复时触发唯一键碰撞。

## TokenBlacklistService 与 Redis 强依赖

### 概述

`TokenBlacklistService` 负责在用户退出登录时将 JWT 令牌加入黑名单（Redis key，TTL = 令牌剩余有效期），防止已注销的令牌被重复使用。**该功能强依赖 Redis**。

### 依赖关系

| 场景 | Redis 状态 | TokenBlacklistService | 行为 |
|------|-----------|----------------------|------|
| 正常 | 可用 | 已注入 | 黑名单写入生效，已注销令牌被拒绝 |
| Redis 未配置/不可用 | 不可用 | Bean 未创建（`@ConditionalOnBean`） | 过滤器检测到 Service 为空，日志输出 `BLACKLIST_UNAVAILABLE`，请求正常放行，**退出登录保护失效** |
| Redis 运行时故障 | 可用→不可达 | Bean 存在但连接失败 | 写入黑名单失败日志 `TOKEN_BLACKLIST_WRITE_FAILED`；检查黑名单时 fail-close（拒绝令牌），日志 `TOKEN_BLACKLIST_CHECK_FAILED` |

### 关键点

- **Redis 是 Token 黑名单的必需依赖，不是可选项。** 虽然代码使用了 `@ConditionalOnBean` + `ObjectProvider.getIfAvailable()` 的"可选注入"模式保证系统在无 Redis 时不崩溃，但这只是一个降级容错设计，**不应视为生产环境的正常运行状态**。
- 如果生产环境出现 `BLACKLIST_UNAVAILABLE` 日志，意味着用户退出登录后 Token 仍然有效，任何持有该 Token 的人都可以继续访问系统，**退出登录保护已完全失效**。
- 同样，Redis 运行时连接故障（`TOKEN_BLACKLIST_WRITE_FAILED` / `TOKEN_BLACKLIST_CHECK_FAILED`）也会导致黑名单功能异常。

### 监控建议

**必须监控以下日志模式**（建议配置告警，阈值 > 0 即触发）：

| 日志模式 | 级别 | 含义 | 严重程度 |
|----------|------|------|----------|
| `BLACKLIST_UNAVAILABLE` | WARN | TokenBlacklistService Bean 未创建，Redis 未配置或不可用 | 🔴 严重 |
| `TOKEN_BLACKLIST_WRITE_FAILED` | WARN | Redis 连接故障，黑名单写入丢失 | 🟡 警告 |
| `TOKEN_BLACKLIST_CHECK_FAILED` | WARN | Redis 连接故障，黑名单检查失败（fail-close，拒绝访问） | 🟡 警告 |
| `BLACKLISTED_TOKEN` | WARN | 检测到已黑名单令牌尝试访问 | ℹ️ 安全事件 |

**生产环境检查清单**：
1. Redis 服务已部署并正常运行
2. 后端 `application-prod.yml` 中 Redis 连接配置正确，`spring.data.redis` 完整
3. 启动日志中 `TokenBlacklistService` 被正常加载（无 `BLACKLIST_UNAVAILABLE`）
4. 运维监控系统已配置上述 4 个日志模式的告警规则
