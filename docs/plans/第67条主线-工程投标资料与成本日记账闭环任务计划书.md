# 第67条主线：工程投标资料与成本日记账闭环

**Goal:** 建设独立“工程投标”模块，只管理公司作为投标人承接工程，提供“投标记录”“投标成本”两个菜单页面；投标记录以独立详情页和四个页签沉淀基本信息及招标文件、投标文件、中标文件的不可覆盖版本，投标成本以 `5401.01 招投标及前期费用` 的启用直接子科目记录关联现金流水；取得有效中标通知书后，系统幂等创建免立项审批的 `PREPARING` 项目。 **Architecture:** 复用现有 `bid_cost` 作为投标记录根、`sys_file` 作为文件内容事实、`cash_journal_entry` 作为唯一现金事实、`bid_deposit` 作为保证金业务事实、`pm_project`、成本科目、RBAC、附件安全、审计及红冲能力；只新增投标文件版本事实、现金日记账显式关联和项目中标来源事实。中标通知书作为项目立项依据，写入“视同批准”状态但不创建工作流实例；不新增投标审批流、独立资金流水表、独立余额、报价组价引擎、外部交易平台同步或自动合同/目标成本生效。

## 1. 已确认需求

- 模块名称：`工程投标`。
- 业务范围：公司作为投标人承接工程；不管理公司作为招标人组织的招标、分包采购或供应商招标。
- 菜单只设两个：`投标记录`、`投标成本`。
- 投标记录使用表格；点击行进入独立详情路由。
- 详情页页签：`基本信息`、`招标文件`、`投标文件`、`中标文件`。
- 招标文件分类：招标文件、清单、图纸；投标文件分类：报价、技术文件、图纸。
- 文件必须保留版本，不允许覆盖正式历史。
- 投标成本为独立业务页面，但现金金额仍以公司统一现金日记账为唯一事实。
- 费用类别只取成本科目 `5401.01` 的启用直接子科目，不允许自由输入或维护第二套类别。
- 模块不使用工作流、不产生审批实例；管理层及以上可直接维护并留审计记录。
- 有效中标通知书替代项目立项审批；标记中标时系统自动创建 `PREPARING` 项目，不再发起 `PROJECT_APPROVAL`。
- 中标来源只豁免项目立项审批；项目启用仍要求目标成本和执行预算达到现有生效条件。
- 默认授权角色：正式 `MANAGEMENT` 管理层角色及 `SUPER_ADMIN`；现有商务经理、项目经理、财务等业务角色不因名称含“经理”自动获得权限。

## 2. 当前事实与缺口

- 当前 `/bid-cost` 只有一个投标成本列表页，详情为页内面板；没有独立详情路由和资料页签。
- `bid_cost` 只有投标编号、项目名称、状态及中标后项目关联，状态仅 `BIDDING/WON/LOST`。
- 现有 API 已覆盖记录 CRUD 和中标/未中标，可保留兼容入口，但中标当前强制先绑定项目，不符合“先登记结果资料”的新契约。
- 当前项目服务只能先创建 `status=DRAFT/approval_status=DRAFT` 项目并走 `PROJECT_APPROVAL`；缺少“中标通知书视同批准”的来源、幂等键和免审创建入口。
- `sys_file` 已提供租户绑定、对象存储、文件类型验证、病毒扫描及 SHA-256 内容寻址，但没有业务版本号、替代链和定版状态。
- `BID_COST` 文件授权当前错误查询目标成本对象；未关联项目的投标资料无法形成可靠授权闭环，必须先修正。
- `cash_journal_entry` 已具备草稿、归档、红冲、账户余额和审计能力，但没有 `bid_cost_id`、`cost_subject_id`、`bid_deposit_id`，不能靠摘要文本做可核对汇总。
- 当前基线只有 `SUPER_ADMIN` 获得投标菜单；没有正式 `MANAGEMENT` 角色，多个 `role_level` 值也不能表达“管理层及以上”，禁止据此猜测权限。

## 3. 范围与非目标

### 3.1 范围

- 顶级“工程投标”导航、两个菜单页面及投标详情子路由。
- 投标记录基本信息、基于正式文件事实的自动状态变化、结果记录和审计日志。
- 中标通知书校验、投标中标与项目创建同事务、项目中标来源追溯及重复中标幂等。
- 三组投标资料的分类、上传、版本、定版、作废、下载和历史查看。
- 投标成本现金流水的投标、成本科目、保证金显式关联。
- `5401.01` 启用直接子科目动态下拉和费用/往来分口径汇总。
- 无审批直接维护、管理层权限、租户隔离、金额并发和红冲一致性。
- MySQL/H2 等义 migration、后端/前端测试、真实角色与浏览器验收。
- 旧 `/bid-cost` 页面和 API 的兼容迁移，不破坏现有投标记录及成本转入事实。

### 3.2 非目标

- 投标立项、报价、技术文件、中标确认或费用登记审批流。
- 定额库、组价引擎、工程量复核、电子签章或在线标书编辑器。
- 自动抓取招标公告、自动连接公共资源交易平台或代替外部投标递交。
- 评标专家、招标方流程、分包商/供应商招标。
- 中标后自动创建合同、自动批准目标成本或自动激活执行预算；既有投标成本转入能力继续独立存在。
- 新建投标现金流水表、余额字段、平行保证金账或前端权威金额计算。
- 修改已应用 migration、清理当前工作树、提交或发布其他任务改动。

## 4. 产品与路由契约

### 4.1 导航

```text
工程投标
├─ 投标记录    /engineering-tender/records
└─ 投标成本    /engineering-tender/costs
```

- `/engineering-tender/records/:id` 是投标记录的详情子路由，不占第三个菜单。
- 旧 `/bid-cost` 在兼容期重定向到 `/engineering-tender/records`；旧书签和既有测试不得直接失效。
- 无 `bid:query` 时顶级目录及两个菜单均隐藏；直接访问路由仍由前端守卫和后端权限双重拒绝。

### 4.2 投标记录列表

列表字段按以下顺序：

1. 投标编号
2. 工程名称
3. 招标人
4. 招标代理
5. 投标负责人
6. 投标截止时间
7. 当前状态
8. 投标结果
9. 最终投标价
10. 投标费用
11. 更新时间

整行可点击；行内按钮不得阻断键盘进入详情。查询条件至少包括关键词、状态、结果、负责人及截止日期范围。

### 4.3 基本信息页签

页面字段：投标编号、工程名称、标段名称、招标人、招标代理、建设地点、招标方式、获取文件日期、投标截止时间、开标时间、投标有效期、招标控制价、最终投标价、状态、结果、结果日期和备注。历史外部平台/编号/链接及负责人ID继续由服务端兼容保存，但不再作为详情页人工录入项。

状态采用最小集合：

```text
PREPARING → SUBMITTED → EVALUATING → WON / LOST → CLOSED
PREPARING / SUBMITTED → WITHDRAWN / TERMINATED → CLOSED
```

- 页面不提供人工状态变更；正式招标文件、投标文件和中标/未中标结果文件分别驱动 `SUBMITTED`、`EVALUATING` 和 `WON/LOST`，不走审批。
- `SUBMITTED` 必须存在当前有效的最终招标文件；`EVALUATING` 必须存在带递交时间的当前有效最终投标文件。
- `PREPARING/SUBMITTED/EVALUATING` 均可继续完善基本信息；结果终态后锁定。
- `WON` 必须存在当前有效中标通知书，并在同一事务中创建或回读唯一 `PREPARING` 项目；不允许用户先手工创建项目再作为中标前置。
- `LOST/WITHDRAWN/TERMINATED` 必须填写原因，并上传结果证据或登记可核对外部来源。
- 状态更新使用条件更新/CAS；写审计日志，记录操作人、时间、前值、后值和原因。

### 4.4 文件页签

| 页签 | 文件分类 |
| --- | --- |
| 招标文件 | 招标文件、工程量清单、招标图纸 |
| 投标文件 | 投标报价、技术文件、投标图纸 |
| 中标文件 | 候选人公示、中标通知书、未中标通知、异议及答复、中标澄清、其他结果文件 |

每一逻辑文件展示文件名、分类、版本号、状态、来源、发布时间/接收时间、上传人、上传时间及替代版本；文件哈希继续由服务端保存和审计，不作为列表列展示。版本状态只保留：

```text
DRAFT → FINAL → SUPERSEDED / VOID
```

- 上传新版本不覆盖 `sys_file` 和旧版本记录。
- 同一逻辑文件版本号单调递增；一次只有一个当前有效版本。
- `FINAL` 后禁止原地换文件、改版本号、作废或用草稿替代；需保留正式证据并以新逻辑文件追加。
- `DRAFT` 可填写原因后作废；物理文件保留。
- 文件内容继续使用通用文件服务的扩展名、MIME、魔术字节、病毒扫描和对象存储契约。
- 文件哈希由服务端计算并写入版本事实；前端不生成权威哈希。

## 5. 投标成本现金日记账

### 5.1 页面定位

“投标成本”是复用公共壳项目上下文的现金日记账业务视图，不是新账本。默认公共项目选择器为“全部项目”；页面不再维护第二个投标选择器和现金概览。列表只读取 `cash_journal_entry`，创建、更新草稿、归档、红冲继续复用现有现金日记状态机；选定项目时投标归属必须与服务端 `bid_cost.project_id` 一致。

页面字段：业务日期、日记账编号、投标编号、工程名称、收支方向、成本科目、摘要、对方单位、金额、资金账户、经办人、保证金类型、附件、状态和原冲关联。

页面顶部服务端汇总：

| 指标 | 权威口径 |
| --- | --- |
| 累计现金支出 | 当前投标有效 `ARCHIVED OUT`，纳入有效红冲净额 |
| 累计现金收回 | 当前投标有效 `ARCHIVED IN`，纳入有效红冲净额 |
| 未退保证金 | 保证金缴纳－退回－没收，以保证金锁定事实回读 |
| 实际投标费用 | `account_category=COST` 的归档净支出；不含保证金本金 |
| 现金净流出 | 归档支出－归档流入，服务端十进制计算 |

### 5.2 成本科目

费用类别禁止自由输入，只允许当前租户 `5401.01 招投标及前期费用` 下状态为 `ENABLE` 的直接子科目：

| 编码 | 名称 | 账户属性 |
| --- | --- | --- |
| `5401.01.01` | 投标费用 | COST |
| `5401.01.02` | 投标保证金 | RECEIVABLE |
| `5401.01.03` | 标书制作费 | COST |
| `5401.01.04` | 招投标代理费 | COST |
| `5401.01.05` | 前期勘察费 | COST |
| `5401.01.06` | 前期咨询费 | COST |
| `5401.01.07` | 前期差旅费 | COST |
| `5401.01.08` | 资格预审费 | COST |
| `5401.01.09` | 履约保证金 | RECEIVABLE |
| `5401.01.10` | 前期其他费 | COST |

- 保存 `cost_subject_id`；响应同时返回当时科目编码/名称快照用于历史展示。
- `5401.01.01` 仅用于无法细分事项，避免和专用科目重复登记。
- 科目停用后不得新增引用；历史流水仍可查询。
- `RECEIVABLE` 科目是往来款：缴纳为 `OUT`、退回为 `IN`，不得进入实际费用合计。
- 保证金没收不是第二笔现金流；应把保证金业务状态转为没收，并形成受控费用/损失事实，禁止再重复记一笔普通 `OUT`。

### 5.3 无审批与状态边界

- 不创建 `wf_instance`、`approval_instance_id` 或任何 `BID_*_APPROVAL` 类型。
- “归档”是现金事实定版，不是审批；不得绕过现有 `DRAFT → ARCHIVED → REVERSED` 及必要 `PENDING_ARCHIVE` 规则。
- 已归档记录禁止修改和删除；纠错只能红冲后重新登记。
- 退款必须关联原保证金及原支出；累计退回不得超过缴纳额。
- 保证金写入、退款、没收、红冲与 `bid_deposit` 聚合回读必须在同一租户、锁定行和同一事务中完成。

## 6. 权限契约

### 6.1 角色

- 新增正式角色码 `MANAGEMENT`，名称“管理层”，默认租户内全数据范围；只创建角色和权限模板，不自动给现有用户分配角色。
- `SUPER_ADMIN` 保持全权限。
- `COMMERCIAL_MANAGER`、`PROJECT_MANAGER`、`FINANCE`、`COMMON_USER` 等不自动继承工程投标权限。
- 禁止使用当前无区分度的 `role_level` 判断管理层；后端以明确 authority 为准。

### 6.2 权限点

复用现有：`bid:query`、`bid:add`、`bid:edit`、`bid:delete`、`bid:status`。

新增最小权限：

```text
bid:file:manage
bid:cost:query
bid:cost:maintain
bid:cost:export
```

- 上述权限和两个菜单仅授予 `MANAGEMENT`、`SUPER_ADMIN`。
- 后端不得继续用通用 `ADMIN` 角色旁路投标接口；超级管理员旁路保持。
- `bid:delete` 仅允许无正式文件、无现金流水的 `PREPARING` 记录；否则只能关闭。
- 文件下载、列表、上传、定版、作废均先验证当前租户投标对象及对应投标权限。
- 因正式文件会自动推进状态，文件写操作同时要求 `bid:file:manage` 与 `bid:status`；`SUPER_ADMIN` 保持旁路。中标建项是受控状态转换的服务端结果，不开放任意项目创建参数。

## 7. 最小数据变化

### 7.1 扩展 `bid_cost`

保留表名和历史 ID，修正其产品语义为投标记录根。新增可空字段承接历史数据：`bid_section_name`、`tenderee_name`、`agency_name`、`project_location`、`tender_method`、`source_platform`、`external_bid_no`、`source_url`、`owner_id`、`document_received_date`、`bid_deadline_at`、`opening_at`、`bid_valid_until`、`ceiling_price`、`final_bid_price`、`result_at`、`result_reason`。

- 金额使用 `DECIMAL`/`BigDecimal`，API 返回普通十进制字符串。
- 旧 `BIDDING` 数据迁移为 `PREPARING`；`WON/LOST` 保持。
- `project_id` 在中标前及未中标记录上可空；进入 `WON` 的同一事务内必须回写系统创建的唯一项目 ID。
- 不在 `bid_cost` 保存投标费用累计、现金余额或文件版本汇总。

### 7.2 扩展 `pm_project` 中标来源

新增可空字段：`source_bid_cost_id`、`initiation_basis`。中标自动立项时：

- `source_bid_cost_id` 指向当前租户投标记录，建立租户内唯一约束，保证一个中标记录只创建一个项目。
- `initiation_basis='BID_AWARD'`，`approval_status='APPROVED'`，`status='PREPARING'`；该 `APPROVED` 表示中标通知书视同立项批准，不存在审批实例、审批任务或审批人。
- 项目名称、业主单位、地址、合同金额及计划日期从投标记录服务端映射；项目编号由服务端按现有唯一规则生成。
- 非中标来源项目保持原 `PROJECT_APPROVAL` 流程，不扩大免审范围。
- 项目进入 `ACTIVE` 仍复用 `ProjectLifecycleService`：必须有已批准且有效的目标成本及其关联有效预算。

### 7.3 新增 `bid_document_version`

最小字段：`id`、`tenant_id`、`bid_cost_id`、`document_group`、`document_type`、`logical_name`、`version_no`、`supersedes_id`、`sys_file_id`、`status`、`current_token`、`content_sha256`、`source_name`、`source_url`、`published_at`、`received_at`、`submitted_at`、`external_receipt_no`、审计字段和软删除标记。

- 唯一约束保证同一租户、投标、逻辑文件、版本号不重复。
- `current_token` 保证每个逻辑文件最多一个当前有效版本。
- `supersedes_id` 必须指向同租户、同投标、同逻辑文件旧版本。
- `sys_file_id` 使用 `RESTRICT`，禁止删除被版本事实引用的文件。

### 7.4 扩展 `cash_journal_entry`

新增可空关联：

```text
bid_cost_id
cost_subject_id
bid_deposit_id
```

- 不新增金额、余额或投标流水表。
- 三个关联均建立租户内索引和可验证外键/服务端归属门；跨租户对象按不存在处理。
- `CashJournalCreateRequest/Query/VO` 增加对应字段；通用现金日记页保持兼容。
- 投标成本查询必须以显式 ID 过滤，禁止通过摘要、项目名或科目名称模糊推断归属。

### 7.5 迁移约束

- 新增下一可用 MySQL/H2 等义 migration；实施时重新检查第66条占用的最高版本，禁止复用或修改已存在 `V267/V268`。
- 所有新增列先允许历史空值；旧记录不回填虚构招标信息、科目或文件版本。
- 菜单、权限、`MANAGEMENT` 角色和默认授权使用同一版本化 migration/启动模板契约，重复升级保持幂等。

## 8. 服务端与 API

### 8.1 投标记录

- 复用 `/bid-cost` CRUD，扩展请求/响应和分页筛选。
- 新增统一状态端点 `PUT /bid-cost/{id}/status`，以目标状态、原因和版本/CAS 更新。
- 旧 `/{id}/won`、`/{id}/lost` 在兼容期委托统一状态服务；不得保留两套状态判断。
- `WON` 服务锁定投标记录，验证中标通知书和项目必填映射，在一个事务中创建项目、写入 `source_bid_cost_id`、回写 `bid_cost.project_id`、更新投标状态并记录审计事件。
- 重复请求按 `source_bid_cost_id` 回读同一项目；任何一步失败则投标状态和项目创建整体回滚。
- 既有成本转入继续复用当前不可变转入事实；项目创建后可进入目标成本/预算准备，但不在本动作中自动批准。
