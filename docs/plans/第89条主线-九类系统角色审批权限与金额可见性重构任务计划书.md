固定规则：

1. 对外角色列表仅显示以上九类；名称、编码、状态和数据范围不可创建、删除、重命名或改写。
2. 公司财务可维护九类角色的目录、菜单、按钮权限包，也可向任意本租户用户分配九类角色，包括自己。
3. 多角色按权限并集生效。`EMPLOYEE + 任一含金额角色` 可见金额并可按专业角色审批；`EMPLOYEE + COMPANY_OWNER/COMPANY_FINANCE` 同时取得 `ALL` 数据范围。此项为已签认规则，不采用 `EMPLOYEE` deny-wins 或互斥。
4. `PROJECT_MEMBER` 只允许访问用户具有有效 `pm_project_member` 关系的项目；项目主表上的经理字段不能代替有效成员关系。
5. 项目成员角色编码体系保持独立，不改 `PM/CM/CSTM/MAT/SUBC/FIN/OTH` 等项目内成员 taxonomy。

### 1.2 公司财务等同超级管理员

`COMPANY_FINANCE` 与隐藏 `SUPER_ADMIN` 采用真实绑定，不引入逐接口别名：

1. 分配 `COMPANY_FINANCE` 时，同一事务自动增加隐藏 `SUPER_ADMIN` 绑定；移除时同步移除。
2. 现有 `SUPER_ADMIN` 用户补充 `COMPANY_FINANCE`；现有 `FINANCE` 用户迁为 `COMPANY_FINANCE + SUPER_ADMIN`。
3. JWT 保留数据库真实角色，因此财务用户同时携带 `COMPANY_FINANCE`、`SUPER_ADMIN`；现有 Spring、`UserContext`、前端管理员判断和直接 SQL 角色检查继续成立。
4. 隐藏 `SUPER_ADMIN` 不出现在角色列表、筛选项、用户角色勾选项或普通角色详情；`PlatformBootstrapService` 创建或接管账号时必须在同一事务绑定 `SUPER_ADMIN + COMPANY_FINANCE`，已完成 bootstrap 不得在重启时静默恢复已被合法移除的权限。
5. 最后一个有效管理员连续性仍是硬门禁。财务可修改自己的角色；若存在替代管理员，可移除自身财务角色，写后授权快照立即失效并要求重新登录。
6. 财务可编辑 `COMPANY_FINANCE` 的业务菜单包，但不能编辑隐藏 `SUPER_ADMIN`。界面必须提示：“移除菜单权限不会撤销超级管理员旁路能力”。
7. 配对生命周期覆盖创建、分配、移除、自删、并发、bootstrap 创建/接管、重启和 token 失效；任何单边绑定均失败关闭并产生审计告警。

采用真实绑定原因：当前大量服务、表达式和 SQL 直接识别 `SUPER_ADMIN`；一次绑定可复用既有行为，避免在数十个模块复制财务特判。

## 2. 菜单、按钮与数据权限

### 2.1 默认导航基线

1. 九类角色默认获得当前全部业务 `DIR/MENU`、父目录及对应只读 `query/list/view` 权限。
2. 权限使用迁移中的显式菜单/权限清单；不使用 `*:query` 模式匹配，不自动继承未来新增菜单。
3. 其他八类角色初始排除“系统管理”整棵目录和“报表中心”目录；公司财务初始拥有全部 `DIR/MENU/BUTTON`。
4. “仅公司财务”是初始权限基线，不是不可修改硬编码。公司财务后续可通过角色权限包授予其他角色；每次变更记录操作者、角色、前后菜单 ID/权限快照和结果。
5. 前端隐藏只负责体验；后端 Controller、服务、数据范围、下载和工作流必须独立拒绝越权直连。

### 2.5 员工自助与金额失败关闭

新增最小正向权限：

- `business:amount:view`
- `purchase:request:self`
- `requisition:self`
- `site:daily:self`
- `schedule:daily-progress:self`

金额规则：

1. `business:amount:view` 初始授予除纯 `EMPLOYEE` 外的八类角色；多角色按并集。

### 3.1 审批人解析与策略

1. 九类系统角色使用 `ROLE + roleCode`。项目级角色还必须是该项目有效成员；公司老板、公司财务按租户级角色解析。
2. 纯员工账号不得成为审批人；员工与专业角色组合时，可按专业角色参与。
3. `ApproverResolver.resolveRole` 在 `requireProjectMembership=true` 时，将本租户启用系统角色用户与该项目活动成员取交集；其他项目同角色人员不得收到任务。模板启用时只做租户级角色/用户/岗位静态校验，项目级可解析性在每次提交时按真实 `projectId` 校验。
4. 默认 `allowAdminFallback=false`，删除现有项目角色找不到时静默回退租户角色/超级管理员的行为；仅公司财务显式开启后才允许。
5. 合同、业主结算、付款申请、项目预算默认：`preventInitiatorApproval=true`、`maxApprovalsPerUser=1`、`allowAdminFallback=false`。提交前必须证明各节点可由满足分离要求的用户完成。
6. 其他流程默认允许发起人命中首节点，但同一用户在一个实例最多批准一次；采购申请单节点允许同角色自批。公司财务可修改这些策略。
7. 复用模板 `conditionRule` 保存严格 `WorkflowSecurityPolicy`：

```json
{
  "preventInitiatorApproval": true,
  "maxApprovalsPerUser": 1,
  "requireProjectMembership": true,
  "allowAdminFallback": false
}
```

只支持以上四个字段、固定类型和边界。`WorkflowTemplateService` 仅对该 schema 解除现有 `conditionRule` 全拒绝，解析、规范化并在引擎执行；迁移前非空旧值不符合 schema 时阻断 G2。模板顺签/会签/或签、节点增删/排序、审批人、金额区间、启停及该策略可完整编辑；尚未接入执行引擎的 `formSchema`、任意节点条件、通过/拒绝脚本和自由 JSON 继续拒绝保存，避免“能配置但不执行”。

模板、节点、顺序和策略每次修改复用现有操作审计，保存操作者、模板 ID、变更类型及规范化 before/after JSON；工作流实例继续保存提交时节点和策略快照。无需新建第二张审计表。

不可配置硬不变量：租户隔离、状态机、幂等、审批审计、运行实例快照和最后管理员连续性。

### 3.2 二十一条工作流执行分母

每个矩阵项必须同时具备：`WorkflowBusinessTypes` 常量、`WorkflowEngine` 提交权限映射、业务访问校验、业务编号解析、提交/重提/撤回入口、模板与节点、终态 handler/副作用、前端提交与待办入口、自动化测试。现有能力逐项复用；缺任一项即不得把模板标记为启用。

当前明确缺口 `BID_COST_TARGET_TRANSFER`、`FINANCE_COST_ALLOCATION`、`QS_RECTIFICATION`、`QS_CONSEQUENCE` 必须补齐上述全链路。前两项最终批准后仍由现有 `CostSubjectV2Service` 权威命令执行转入/分摊，审批实例 ID 与业务 ID、租户、项目必须一致；后两项按第 3 节质量状态机执行。冲销流程不在用户本次二十一行矩阵内，保持现有独立审批契约，不被本轮静默改线。

## 7. 风险、金丝雀与恢复矩阵

| 风险/触发 | 预防与验收 | 恢复 |
| --- | --- | --- |
| 任一财务账号泄露即全平台超管 | 明示风险、最少账号、登录/授权/菜单/流程变更审计 | 立即停用账号、移除财务/超管成对绑定、授权快照使旧 token 失效 |
| 财务与隐藏超管绑定漂移 | 事务写、迁移回读、启动契约测试 | 用下一版本 forward-fix 恢复成对关系；禁止手改旧 migration |
| bootstrap 重启后产生单边角色或静默提权 | 创建/接管原子配对；完成态不自动再授权；重启契约测试 | 停止 bootstrap，按审计和备份恢复合法配对，再使旧 token 失效 |
| 员工全业务读取泄漏金额 | 服务端正向权限、显式目录、未知字段测试失败、下载独立拒绝 | 先撤销员工业务查询菜单，再修复目录；不得仅隐藏前端 |
| 回滚旧后端但保留扩权数据库 | 回滚演练固定顺序 | 先用 forward migration 撤销员工扩权/新绑定，再回退代码；禁止旧后端直接连扩权库 |
| 旧角色或模板漏迁导致无审批人/超管兜底 | 启用模板全扫描、提交预检、默认无 fallback | 禁用受影响模板，用 forward-fix 修正编码后再启用 |
| 高风险流程同人多节点 | 四类默认发起人隔离、每人最多一次、提交前基数校验 | 公司财务按审计配置补足账号或显式调整策略；不得直接改运行实例 |
| 质量安全审批与原状态机双写 | 关闭直接 post/reinspect 绕行，最终 handler 同事务 CAS | 回滚本任务代码；已迁状态只用更高版本和领域补偿命令修复 |
| 年/季/月/周层级或日期越界 | 复用现有父子周期和日期校验，补层级/重叠测试 | 禁用新建年/季入口；保留既有月/周事实，不删历史 |
| 角色/菜单修改后页面使用旧授权 | 现有授权快照校验、401 后重新登录 | 重新登录；不放宽快照验证 |
| H2/MySQL 语义漂移 | 同号 migration、fresh/upgrade 四路径测试 | 停在 G2，用下一可用版本前滚修复 |
| 覆盖本任务外脏改动 | 独立 worktree、精确 diff、禁止批量暂存 | 只撤销本计划自有文件；禁止 reset/checkout 他人成果 |

本地金丝雀顺序：

1. 公司财务账号：系统/报表、角色自分配、流程编辑、隐藏超管和 token 失效。
2. 纯员工账号：全业务菜单、项目成员边界、DOM/JSON/下载无金额、四类自助。
3. 项目经理账号：项目成员数据范围、金额可见、指定审批。
4. 再覆盖其余六类账号和二十一条模板；无未分类失败后才进入 G5。
