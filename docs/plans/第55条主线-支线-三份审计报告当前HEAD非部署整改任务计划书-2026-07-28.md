## 2. 阶段与实施

1. refresh Cookie Path 从 `/api/auth/refresh` 改为 `/api/auth`；暴露范围仍限认证端点。
2. `AuthService.isCurrentAuthorization` 将 token 中角色/权限集合与数据库当前集合比较。
3. `JwtAuthenticationFilter` 在凭据检查后执行授权快照检查；不一致立即返回 401。
4. refresh token 仍只校验用户、租户、状态和密码版本；角色变化后可换取只含当前权限的新 access token。
5. 补 Cookie Path、授权快照不一致和过滤器拒绝测试。

## 3. 验收

- 登录下发 refresh Cookie 包含 `Path=/api/auth`；logout 请求可携带并拉黑它。
- 密码、状态和租户检查保持原行为。
- 角色分配、角色菜单或系统权限集合变化后，旧 access token 下一请求返回 401。
- 旧 refresh token 只能换取当前服务端角色/权限，不恢复旧 authority。
- 目标认证测试、后端构建及同 HEAD 门禁通过。

## 4. 风险与回滚

| 风险 | 控制与回滚 |
| --- | --- |
| 每请求增加角色/权限查询 | 安全路径优先；后续仅在有性能证据时引入授权版本列 |
| 历史 token claim 格式 | 同时兼容列表、逗号字符串和 gzip 权限 claim；解析失败 fail-close |
| 权限变化导致用户立即掉线 | 预期安全行为；重新登录取得当前授权 |
| Cookie 暴露扩大 | 仅从单端点扩大到 `/api/auth`，仍不发送到业务 API |

回滚代码提交即可恢复原行为；不涉及 migration、历史数据或生产状态。
