## 2. 范围、非目标与不变量

### 2.1 范围

- `CL-01`～`CL-17` 的代码、最小数据预检、相关前端入口和回归测试。
- `D-01`～`D-10` 的业务决策卡；只有签认项才进入对应实现包。
- 合同、收入/应收/回款、销项/进项发票、付款条款、供应商退货、计划/日报/技术、变更成本、库存在途、动态成本、月结和领域审计。
- H2、loopback MySQL、真实 V2 页面和现有本地 Live/contract E2E 中受影响链路。

### 2.2 非目标

- 不建设通用权限中台、MyBatis 自动数据范围、通用状态机、通用冲销平台、数据仓库或消息总线。
- 不新建供应商退货事实表、应收类型、文件主表或第二套项目计划。
- 不自动回填无法从唯一事实推导的供应商退货明细、签证 WBS、合同终态或财务分配。
- 不把工作日历、预测、考勤、工资、设备、BIM、全业务移动端、外部财务集成或竣工档案产品化带入本轮。
- 不规划生产、目标环境、远端数据库、RC workflow、部署、Tag 或 Release。
- 不授权生产/目标环境、强推、绕过保护、Tag、Release 或部署；本地实现与受保护 Git 交付已授权。

### 2.3 不变量

1. 租户隔离和项目数据范围必须同时成立；隐藏按钮不能替代服务端校验。
2. 回款、开票、结算、库存、成本和会计副作用必须在同一权威命令中原子提交；失败为零部分写入。
3. 已验证附件、已生效计划、已关闭期间和历史审计不可被普通编辑路径改写。
4. 状态转换必须由可回读业务事实驱动，不能靠手工 SQL、客户端计数或自由文本证明。
5. 历史未知关系保持未知；不得为通过迁移或测试伪造分配、WBS、附件、结算或归档。
6. 既有 COMPLETE 域只做回归；没有当前价值和验收的“PARTIAL”不等于必须开发。
7. AR/AP 关账必须比较业务子账与已过账总账两个独立事实源；同表派生值相等不构成对账通过。

## 3. 最小实施设计

### 3.1 Codemap 与影响面

- 实施前比较当前仓库与 `docs/codemap/codemap.lock`；当前 lock 不绑定本计划基线，代码变更前必须重新生成并回答调用方、影响面和测试覆盖。
- 只有模块边界、路由、表或主要数据流发生变化时随代码提交 codemap 产物；本轮计划编制不改 codemap。

### 3.2 项目授权单点复用

- 建立受影响端点清单：列表、详情、余额、创建、编辑、删除、提交、复核、导出、快照、预测和审计查询。
- 资源型入口从权威对象反查 `project_id` 后调用 `checkAccess()`；列表把 `accessibleProjectIds()` 放进数据库谓词，空集合返回空，不先拉全租户再内存过滤。
- 真正租户级的财务对账、客户信用和集成动作只允许管理员或 ALL 数据范围；不得向项目成员暴露全租户结果。
- 不新增 resolver 接口、注解扫描器或 MyBatis 拦截器；用架构契约测试锁定明确端点分母。

### 3.3 合同终态与收尾事实

- `SETTLED` 命令锁定合同和对应终局事实，再按 `D-02` 的合同类型矩阵做幂等 CAS；保留 `TERMINATED` 独立语义。
- MAIN 复用已批准业主最终结算；SUB 复用已批准最终分包结算。PURCHASE/LEASE/SERVICE 未签认前不猜测。
- 结算被合法撤销或纠正时，必须在同一事务恢复合同状态或明确拒绝；关闭门继续要求全部合同终态。
- 竣工结算的普通应收统一读现有 `PROGRESS`，质保金继续读 `RETENTION`；删除测试手工构造 `REGULAR` 的假阳性路径。

### 3.4 收入、开票与回款证据顺序

- 回款创建只保存草稿和幂等上下文，不改变应收、现金或凭证；文件中心确认存在同租户、同业务对象、CLEAN 银行回单后，confirm 锁定应收并一次性完成全部副作用。
- 同一外部流水号与幂等键并发只能形成一组回款/分配/现金/凭证；重复相同请求返回原事实，不同载荷冲突。
- 销项发票创建只形成无有效应收分配的 `PENDING_EVIDENCE`；服务端不信任客户端附件计数，上传失败时有效分配必须为零。
- 确认/复核事务从文件中心查询同租户、同业务对象的 CLEAN 发票附件，锁定应收和已有有效分配，校验累计可开票额后原子激活分配并同步 `VERIFIED/REJECTED` 状态；公式由 G1 固定，验证后附件不可变。
- 手工业主结算入口按 `D-01` 裁决；默认不允许无来源记录进入核心结算、应收和关闭指标。

### 3.5 供应商退货单一写权威

- 保留 `MatSupplierReturnService` 的明细、幂等、库存、成本、订单/AP 和撤销逻辑。
- 旧寻源 POST/confirm 不得把贫化表头委托给正式服务；直接失败关闭并迁移 V2 页面到正式请求模型。
- 旧 GET 如需保留，只返回正式表头/明细投影；绩效统计只认已确认且未撤销的正式记录。
- G0 统计表头无明细历史。为零则无需迁移；非零时隔离为只读异常，除非存在唯一可证明明细，否则禁止自动补造。

### 3.6 计划、日报、技术与变更

- PREPARING 且无基线时才能普通创建 BASELINE；ACTIVE 项目只走现有纠偏单→REVISION→复制 WBS/实际进度链。
- WEEKLY 审批对同租户、同 ACTIVE 基线、同类型区间加锁查交叠；相邻边界按明确闭区间规则验收。
- 日报提交重新加载当前日期对应周计划及任务集合，逐行核对四元组；失败不得推进 WBS 或创建快照。
- 施工完成和最终关闭门新增技术四类 blocker；只看当前有效版本和活动事实，SUPERSEDED/跨租户记录不误阻塞。
- 新签证明细绑定 ACTIVE WBS 并传播到 `CostItem.wbsTaskId`；`impactDays` 在 `D-07` 前不触发自动排程。

### 3.7 在途与成本投影

- 在途订单只认 `PERFORMING/PARTIAL_RECEIVED`，`COMPLETED/CANCELLED` 排除；剩余量为订单量减已接收/已退回的既有权威口径。
- 科目 ETC 读取最新有效 `cost_forecast_item.estimated_remaining_amount`；无分配为零或显式未分配桶，不能把项目总额复制给每一科目。
- 项目合同收入、确认收入和预计利润保留在项目汇总；科目行只表达可归属的成本事实。

### 3.8 AP 票款、付款条款与月结

- AP 发票先绑定付款申请还是先绑定成功付款由 `D-03` 决定；复用现有可空字段和 `invoice_payment_allocation`，核验前要求真实 CLEAN 发票，付款后显式分配，禁止自动删除已核验分配。
- 仅当 `D-04` 签认“付款必须绑定条款”时，选择单条款外键或最小多条款分配表，并由部分付款、成功付款和冲销驱动条款金额、状态和实付日期；若签认条款仅作合同信息，则只回归比例合计 100%，不新增关系或派生状态。
- 保留现有银行回单与业务支付/回款交叉对账。AR/AP 另从业务子账计算期末余额，并从已过账 `accounting_entry/accounting_entry_line` 按 `D-09` 科目和方向计算总账余额。
- `D-09` 固定分录矩阵：AR 确认先借记 `1122 应收账款`，回款再贷记冲减；AP 确认先贷记 `2202 应付账款`，普通付款再借记冲减；无已确认 AP 的 `ADVANCE` 付款进入预付账款，并在后续 AP 确认时显式重分类。月结必须用非零 AR/AP 余额验证差异为零；不得新增第二 AP 台账、数据仓库或“对账平台”。

### 3.9 高风险操作审计

- G1 只把金额、付款、发票核验、冲销、月结及其他被明确签认的关键成功事件列为 mandatory；同时冻结唯一计数键 `(tenant,event_type,business_type,business_id,idempotency-key)`，不把 249 个注解全部改成强事务。
- mandatory 事件复用所在领域既有审计载体，与业务状态和金额在同一事务写入；审计写失败必须回滚业务。每个唯一计数键恰一条，幂等重放不增量；`finance_audit_event/revenue_audit_event` 的 `payload_json`、`payload_hash`、主体、操作者和关联 ID 必须可回读。
- `sys_operation_audit_log` 继续记录普通查询、失败尝试和 HTTP 轨迹；写失败计数并告警，但不作为关键业务成功的完整性证明。
