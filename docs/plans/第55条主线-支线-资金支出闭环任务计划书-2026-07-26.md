# 第55条主线支线：资金支出闭环任务计划书

**Goal:** 以 `docs/business/project-payment-closed-loop.md` 为唯一业务标准，修复当前“核心付款链可运行，但合同预算、审批重提、预算消耗时点、权限、显式关系、发票不可变、驾驶舱口径、Trace 与完整 E2E 未闭合”的差异，使任一资金支出可从项目正向走到现金日记、发票和凭证，并可从任一核心事实反向追溯到项目、合同、来源申请、审批与预算台账。

**Architecture:** 复用现有 Project、ProjectBudget/Line/Ledger、Contract、Expense、Settlement、PaymentApplication/Source、Workflow、PayRecord、CashJournal、InvoiceAllocation、AccountingEntry、Dashboard 与 PaymentTrace；不重建第二套资金、预算、审批、附件、发票或凭证体系。服务端数据库事实、`BigDecimal`、显式关系、不可变台账、事务和幂等键为权威，前端只提交意图并写后回读。最小方案只修复已确认闭环断点，禁止顺带新增银行直连、税务平台、集团资金池、多币种、自由工作流、通用低代码或无调用方抽象。

优先级：`P0`

状态：`S1—S4 本地实施与验收通过 / PPCL-11 同HEAD CI待执行 / 生产阻塞`

## 4. 业务不变量

1. 金额均以服务端 `BigDecimal` 和十进制字符串为准；前端不得计算权威余额、执行率、利润或状态。
2. 项目、合同、预算、申请、审批、付款、日记、发票、凭证必须同租户、同项目。
3. 项目非 ACTIVE、合同非 PERFORMING、预算非 ACTIVE 或合同关闭/终止时禁止新增或提交付款申请。
4. 提交前必须校验项目、合同、预算、来源、费用分类、付款对象、附件和金额；失败不得创建审批或新增/重复占用。
5. EXPENSE来源沿用费用申请原预算占用，付款申请只冻结可转换额度；其他来源由PAY_REQUEST占用。驳回/撤回按来源释放一次；重提进入 `round+1` 并按来源重新冻结或占用一次；历史审批不可覆盖。
6. PayRecord SUCCESS、CashJournal ARCHIVED、Budget CONSUMED、Voucher POSTED 是四个独立事实。
7. 外部流水、付款、自动日记、预算台账和自动凭证均有不可绕过的唯一幂等键。
8. 已付款、已归档、已核验、已分配、已过账事实不可直接修改或硬删除，只能受控冲销或红冲。
9. Dashboard 指标可从底层事实重算，详情合计必须等于汇总。
10. Trace 缺链时必须明确失败或告警，不能返回半链并宣称成功。

## 5. 权威事件与金额时点

| 事件 | 预算占用 | 预算消耗 | 现金余额 | 凭证 |
| --- | --- | --- | --- | --- |
| EXPENSE提交 | 由Expense增加 | 不变 | 不变 | 无 |
| EXPENSE来源付款申请提交 | 只冻结可转换额度，不二次占用 | 不变 | 不变 | 无 |
| 其他来源付款申请提交 | 由PAY_REQUEST增加 | 不变 | 不变 | 无 |
| 驳回/撤回 | EXPENSE释放可转换额度；其他来源释放PAY_REQUEST占用 | 不变 | 不变 | 无 |
| 重提 | EXPENSE重新冻结可转换额度；其他来源以新round重新占用 | 不变 | 不变 | 无 |
| PayRecord SUCCESS | 保留对应待归档占用 | 不变 | 不变 | 可生成 DRAFT，不得 POSTED |
| CashJournal ARCHIVED | 对应占用转出 | 增加对应金额 | 按归档流水更新 | 绑定 CashJournal 后允许复核/过账 |
| 归档前撤销 | 恢复付款来源与可付额度；占用不重复 | 不变 | 不变 | 取消或冲销 DRAFT |
| 归档后冲销 | 按反向台账恢复或重新占用 | 反向台账冲销 | 归档红字日记恢复 | 生成冲销凭证 |

### S1：审批状态机、状态与权限

任务：

1. 在 budget 域补 `ContractBudgetAllocation` 最小 Service/Controller；分析导入逻辑不再承担日常入口。

1. ACTIVE 项目、ACTIVE 预算、PERFORMING 合同和合同预算分配成立。
2. 费用或结算来源提交后只占用一次预算并进入多级审批。
3. 驳回后释放，重提形成 `round+1`，旧记录保留。
4. 两次部分付款分别生成成功付款和唯一 PENDING_ARCHIVE 日记。
5. 归档前预算不消耗、现金不变化；归档后逐笔转消耗并更新现金。
6. 发票跨两笔付款分配守恒，必要证据齐全，凭证借贷平衡。
7. Dashboard 合同、付款、预算执行、现金流、利润与底层事实一致。
8. 从现金日记、发票和凭证均能反查完整链。

负向必须覆盖：项目暂停、合同关闭、预算不足、附件缺失、付款对象错误、费用分类缺失、DIRECT无权限、审批驳回、重复提交、重复付款、重复归档、已分配发票删除、并发、冲销、跨项目和跨租户。

## 10. 金丝雀

只允许 dev/test/demo：

1. 单租户、单项目、单合同、单预算科目和单资金账户。
2. 执行“提交→驳回→原实例重提→多级审批→分次付款→现金归档→发票分摊→凭证→全链追溯→冲销”。

5. 数据库恢复只使用前向修复 migration；不得删除或修改已应用 migration。

## 11. 恢复与回滚

| 故障点 | 必须保持的状态 | 恢复方式 |
| --- | --- | --- |
| 审批创建失败 | 无审批孤儿、无新增或重复占用；EXPENSE原占用不丢失 | 整体回滚后按幂等键重试 |
| 驳回后重提失败 | 原实例和旧轮次仍可查，预算已释放 | 修正后走专用重提，禁止创建替代业务链 |
| 付款成功、日记未归档 | Payment=SUCCESS、Journal=PENDING_ARCHIVE、预算仍 RESERVED | 完成归档或正式冲销，禁止手工改账 |
| 归档中预算/余额/凭证失败 | Journal保持PENDING_ARCHIVE，预算和余额不变化 | 整体事务回滚后重试 |
| 并发或重复付款 | 最多一笔有效成功事实 | 业务锁、唯一流水号和幂等键共同控制 |
| 合同预算不足 | 不创建工作流、不占项目预算 | 调整合同分配后重新提交 |
| 附件缺失/扫描失败 | 禁止付款、归档或核验 | 补传合规附件后重试 |
| 跨租户/跨项目 | 零写入、零数据泄漏 | 返回拒绝或NOT_FOUND |
| migration有孤儿 | migration fail-close | 输出差异报告；目标环境治理归既有发布门 |
| Dashboard对账不平 | 不用0或估算掩盖 | 按交易事实对账并告警 |

已产生财务事实后，代码回滚不得直接删除数据；必须通过业务冲销或前向 migration 恢复。仅在未产生业务数据且另有 Git 授权时允许回退代码提交。
