# 第90条主线：资金与成本字段权威源及模型收敛

## 1. 二次复核裁决

### 1.1 基线与运行态事实

1. `master` 与第89条主线独立 worktree 当前均基于 `ce669b33`；第89条主线存在大量未提交中间态，不能当作第90条的稳定实施基线。
2. 当前 backend 容器实际 datasource 为 `jdbc:mysql://mysql:3306/cgc_pms_demo_ui_20260728`，该库 Flyway 已到 `V291`，有 214 张表。
3. 实际 datasource 中本计划关键表大部分为空；`cash_journal_entry` 有 1 条 `OUT / ARCHIVED / MANUAL / 10000.00`，`fund_account` 有 1 条；无会计分录孤儿，`overhead_allocation_record` 为 0 条。样本过稀，不足以支持删列裁决。
4. 容器默认旁库 `cgc_pms@V284` 不是当前 backend datasource；该库有 13 条无头 `accounting_entry_line` 和 1 条零金额 `DRAFT overhead_allocation_record`。本计划不修复该旁库，但 G0 必须用数据库名白名单防止误选、误验收或误清理。
5. 项目数据库规范明确区分 `approval_status` 与业务 `status`，并要求历史快照、永久幂等事实、活动唯一键保留。因此“把所有状态合成一列”不通过二次复核。

### 1.2 对首次建议的校正

| 首次建议 | 二次裁决 | 原因 |
| --- | --- | --- |
| 合并 `approval_status` 和 `status` | 否决 | 审批和业务生命周期是正交维度；应修正语义，不应合并 |
| 删除所有活动标识 | 部分否决 | 人工双写的 `is_active/active_flag` 可收敛；数据库生成的活动唯一键必须保留 |
| 立即合并 `pay_application_basis` 和 `payment_application_source` | 降级为 G1 决策项 | 两表分别可表达审批证据与资金消耗来源；未证明 1:1 前不合并 |
| 将 `default_target_ratio` 移入版本表 | 暂不实施 | 当前十类比例是固定默认，最终明细金额已快照；无多模板需求时增表属过度设计 |
| 全域增加币种/汇率字段 | 暂不实施 | 当前规范明确金额为人民币元；未有多币种业务决策 |
| 立即删除 `overhead_allocation_record` | 保留为受控退役候选 | 运行代码为 0 引用，但旁库仍有历史行；需精确数据库和归档裁决 |

### 1.4 明确保留，不进入删减

- `approval_status` 与业务 `status`：维度不同，只修语义和转移约束。
- `apply_amount/approved_amount/actual_pay_amount`：申请、批准、实付三个事实阶段。
- 各粒度 `paid_amount`：合同、付款申请、来源行、结算和计划的粒度不同，只能统一命名与对账。
- `gross/net/tax/tax_rate`：法定单据和历史快照，保留并增加守恒校验。
- `source_contract_amount/target_cost_rate`、预测公式结果、账龄/报表快照：需与 `formula_version/source_cutoff_at` 一起保留。
- 预算行当前 `reserved_amount/consumed_amount` 与 `budget_ledger` 事后余额：前者用于并发裁决，后者用于审计和重放。
- 工作流申请快照与最终记账事实：申请可驳回/撤回，最终事实只能冲销，禁止合表。
- `active_unique_token/active_guard/idempotency_key/version/deleted_flag`：完整性和并发技术列，不按“前端不展示”判废。
- `external_sync_status/external_sync_at/collection_record_id/period_id/adjustment_flag`：已有 SQL 或服务闭环消费，不因某个实体未映射就删除。
- `default_target_ratio`：继续作为固定十类初始分配参数；只有出现多模板业务需求时重开版本化。

## 3. 核心不变量

1. 每个金额字段必须标记为以下且仅以下一类：用户输入、外部原始事实、审批快照、不可变记账事实、并发余额、派生结果、报表快照。
2. 同一粒度只有一个权威写入者；缓存/快照必须有公式版本、来源截止时间或对账入口。
3. 所有实际成本、付款、回款、预算消耗和会计凭证事实保持永久幂等；纠错只新增冲销/调整事实，不改写历史原件。
4. 审批状态、业务状态、支付/收款结果状态可同时存在，但必须有正交语义、状态组合矩阵和单一转移服务。
5. 租户、项目、合同、业务来源、资金账户和成本科目关联必须一致；多态关联登记且 fail-closed。
6. 头表合计、明细合计、台账差额和原始事实在同一事务写后回读守恒；不允许“页面显示对”替代数据库事实。
7. 精度统一为人民币元 `DECIMAL(18,2)`；数量、比例、单价使用已签认精度，不在模型收敛中暗改舍入口径。
8. API 过渡期可读旧字段别名，但服务端只写新权威字段；未知旧新冲突必须拒绝，不静默选一个。
9. 新旧字段对比、数据预演、备份和恢复验证未通过时，禁止删列、删表或移除兼容读。

## 4. 目标数据契约

### 4.1 字段权威源登记表

实施时新增可审查的字段契约文档，每个范围内金额/状态/来源字段至少记录：

| 属性 | 含义 |
| --- | --- |
| 表、字段、数据粒度 | 精确物理定位和业务对象 |
| 权威类型 | 输入/原始事实/快照/记账事实/余额/派生/报表 |
| 写入者 | 唯一 Service/Handler/Mapper 入口 |
| 计算公式和舍入 | 精确公式、空值、负数、冲销和尾差口径 |
| 来源与对账 | 权威明细/事实表、对账 SQL 与误差必须为 0 |
| 租户/项目/状态约束 | 读写范围和允许状态 |
| API/页面消费者 | DTO、导出、文档、看板和表单 |
| 退役策略 | 保留/改名/派生/归档/删除及兼容窗口 |

建议文档：`docs/database/finance-cost-field-authority.md`。该文档是契约清单，不重复数据库自动字典。

### 4.2 目标成本状态

- `approval_status`：`DRAFT / APPROVING / APPROVED / REJECTED`，仅由工作流驱动。
- 业务版本状态：`PRE_ACTIVE / ACTIVE / SUPERSEDED / CANCELLED`，仅表达版本是否当前生效。
- `is_active` 过渡期由业务状态派生；合同前必须证明旧新字段对比为 0 差异。
- 同项目只有一个 `ACTIVE` 版本，由生成活动键和唯一约束保证，不依赖先查后写。

### 4.3 执行预算

G1 必须确认 `project_budget` 是否已全面收敛为“每项目一条滚动执行预算投影”。若成立：

- 权威来源为已批准目标成本的责任金额。
- `source_cost_target_id` 保留，表示当前投影来源。
- `budget_amount/reserved_amount/consumed_amount` 保留，分别表示限额、占用和消耗。
- `approval_status/active_flag/version_no` 若永远为常量，列为退役候选；`status` 收敛为投影可用状态。
- `budget_ledger` 永久保留；调整台账的 `business_id` 继续指向对应目标成本版本，不被当前头部覆盖。

若仍存在合法独立项目预算，上述退役取消，保留审批和版本状态。

### 4.4 派生金额

以下字段不得由客户端作为权威值写入：

- `cost_target.total_target_amount/total_bid_cost_amount/total_responsibility_amount`：从明细求和。
- `project_budget.total_amount`：从有效预算行求和。
- `collection_record.unallocated_amount = amount - allocated_amount`。
- `account_receivable.outstanding_amount = original_amount - collected_amount - credited_amount`。
- `stl_settlement.unpaid_amount = final_amount - paid_amount`。
- `finance_account_reconciliation.difference_amount = expected_amount - ledger_amount`。
- `payment_schedule.paid_amount`、`collection_schedule.collected_amount`、发票分配合计：由不可变分配/支付/回款事实控制。
- 资金预测行的 `projected_balance/gap_amount/inflow_variance/outflow_variance`：作为版本快照保存，但只能由同一公式服务生成。

并发余额和历史快照不必强制改为生成列；必须根据写入频率、锁定语义、冲销和历史口径选择。

### 4.5 付款来源与冲销

1. 对每个 `pay_application_basis` 和 `payment_application_source` 结合检查基数、金额、来源类型和上下游分配。
2. 若是 1:1 同语义，扩展为单一付款申请来源行；若是多证据对一金额来源，保留两表并新增明确关联。
3. `payment_application_source` 的泛化关联与专用 ID 必须满足 XOR/类型一致，且在租户、项目、合同和金额上一致。
4. 新冲销记录使用 `reversal_of_id`指向原付款；原付款不再用同一列反指新冲销。保留原付款 `REVERSED` 状态和冲销生效时间，并以唯一索引保证一个原付款最多一个有效全额冲销事实。

### 4.6 页面与用语

现有“项目适用与目标成本”和“影响与转入追踪”必须拆解为用户可理解的任务，不再把字段实现细节暴露为页面概念：

- “项目成本科目适用范围”：仅管理项目可用科目白名单及 `ALL/WHITELIST` 模式。
- “归集规则”：业务来源/分类/项目自动命中成本科目。
- “科目转换规则”：同一科目树中的来源科目到目标科目规则，不再称“旧科目迁移”。
- “科目影响分析”：只展示各业务引用数和禁用/调整前影响。
- “投标成本转入”和“财务费用分摊”：分开展示申请、审批、记账事实和冲销追踪。
