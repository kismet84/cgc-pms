## 性能问题与优化策略

### PERF-20260811-001：全项目视图无界并发扇出

- **优先级：** P1
- **证据：** `TechnicalManagementPage.vue` 为 `N` 次请求，`QualitySafetyPage.vue` 为 `2N`，`ProjectCloseoutPage.vue` 为 `N`，`SupplierSourcingPage.vue` 为 `3N+1`。前端取全部数据后才以 `slice` 显示 10 条。
- **影响：** 请求数 `O(N)`，浏览器内存为所有项目返回记录总和。供应商页 11 个项目即产生 34 个业务请求，超过 Nginx `burst=30`。
- **策略：** 后端提供按可见项目聚合的真分页端点；前端每次交互只请求当前页。不增加前端全量缓存。
- **本轮未改原因：** 需统一调整四组前后端分页契约，限流并发池只能规避 429，不解决全量内存。
- **验收：** 50 个可见项目时，首页每个业务视图仅 1 个数据请求；返回不超过页大小；翻页不预取全量；无 429。

### PERF-20260811-002：通讯页串行拉取并渲染全部历史

- **优先级：** P1
- **证据：** `loadAllMessages` 按 100 条从 `afterSeq=0` 串行拉到末页，然后渲染全部 `<article>`。1 万条消息为 100 个串行往返和约 1 万个消息节点。
- **已完成子项：** 切换会话时中止旧请求，防止无效网络、解析和分配。
- **策略：** 新增向前游标契约；首次只取最新 50–100 条，向上滚动再读旧页，客户端保留固定消息窗口。无需新增虚拟列表依赖。
- **本轮未全改原因：** 当前 API 只有 `afterSeq`，不能从最新页向前翻页；需先固化后端游标、已读位点和 SSE 去重契约。
- **验收：** 1 万条历史时首屏 1 次请求、DOM 不超过窗口上限；上拉、SSE 追加、去重和已读位点保持正确。

### PERF-20260811-003：付款追踪全链路多层 N+1

- **优先级：** P1
- **证据：** `PaymentTraceService` 先读全部付款申请，再逐条调用 `byApplication`。每个申请重读项目、合同、审批、来源、付款、发票、凭证和项目全部预算台账。查询数至少约 `9K`，关联齐全时可达每申请二十余次；预算数据传输为 `K×L`。
- **策略：** 以申请 ID 集合为入口，每张关系表执行一次 `IN` 查询并分组组装；单申请入口复用单元素批量路径。预算台账直接按业务键查询并命中现有索引。
- **本轮未改原因：** 涉及金额、权限与多业务关联的响应组装，需独立查询数回归和金额对账，不与 Shell 小修混改。
- **验收：** 1/10/100 个申请时查询数为常数级；插入 10,000 条无关预算台账不增加传输行；原响应图、权限与金额完全一致。

### PERF-20260811-004：现金摘要全量装载与账户 N+1

- **优先级：** P1
- **证据：** `CashJournalService.summary` 将全部有效流水装入实体后求和，再加载全部待归档流水仅取 `size()`，并为每个资金账户单独执行余额 `SUM`。数据查询至少 `A+3`，JVM 分配 `E+P` 个流水对象。
- **策略：** 有效流水用一条 `SUM(CASE...)`，待处理用 `COUNT(*)`，账户余额按账户类型一次分组聚合；可访问项目 ID 只解析一次。
- **本轮未改原因：** 摘要包含日期、账户、投标和权限特殊语义，需 H2/MySQL 双方聚合测试。
- **验收：** 1/100 个账户时查询数恒定；10 万流水时返回金额与原实现一致；不装载流水实体。

### PERF-20260811-005：应收账龄重复扫描同一结果集五次

- **优先级：** P2
- **证据：** `RevenueAdvancedService.aging` 连续调用五个账龄桶；每个桶都读取项目全部未结应收并在 Java 过滤。固定 5 次往返、`5R` 行传输/Map 分配和 `5R` 次日期计算。
- **策略：** Java 预计算日期边界，单条 SQL 用五个 `SUM(CASE WHEN due_date ... THEN outstanding_amount END)` 返回单行；不使用方言化 `DATEDIFF`。先 `EXPLAIN`，仍扫描明显时再以新 Flyway migration 增加复合索引。
- **本轮未改原因：** Codemap 未单列 revenue 调用和测试边界，且当前 Codemap 文件已有其他工作树改动；先补地图覆盖，再改金额查询。
- **验收：** 覆盖逾期天数 `-1/0/1/30/31/60/61/90/91`；五桶金额正确；查询数严格为 1；H2 与 MySQL 均通过。
